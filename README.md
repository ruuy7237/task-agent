# task-agent

> 从零手写的 Tool-Calling Agent —— 不用任何 agent 框架，把「任务拆解 → 工具调用 → 结果校验 → 失败恢复」每一步都写清楚，并用 **51 条任务评测集**量化每一次改动。

![python](https://img.shields.io/badge/python-3.9%2B-blue)
![deps](https://img.shields.io/badge/dependencies-stdlib%20only-green)

## 为什么做这个项目

Agent 开发实习的要求里反复出现这几句话：**任务拆解、工具调用、结果校验、设计测试任务并记录结果、分析失败原因**。市面上大部分 demo 停在「能跑通一次」，而真正工程化的部分是：它是怎么失败的、失败怎么被发现、以及下一次怎么不失败。

所以这个项目刻意不用 LangChain 的 Agent 抽象，而是手写整个循环，并把「校验」做成可开关的开关，让 **没有校验的朴素版** 和 **带校验的加固版** 在同一套评测集上对照。

## 快速开始

```bash
git clone https://github.com/ruuy7237/task-agent.git
cd task-agent

# 已接入 DeepSeek：项目根目录的 .env 里放好 LLM_API_KEY，默认就走真实模型
python cli.py --task "先算出研发部平均工资，再算出销售部平均工资，告诉我差多少"

# 想退回离线 mock（不联网、不花钱）就删掉 .env，再跑：
python cli.py

# 跑完整评测
python evals/gen_tasks.py       # 生成评测集
python evals/run_eval.py        # 跑分并生成 evals/report.md
```

**零第三方依赖**：全部用 Python 标准库实现，clone 下来不用 `pip install` 就能跑。

## 架构

```
用户任务
  │
  ▼
LLM ──tool_calls──▶ 参数校验（JSON Schema）──▶ 工具执行 ──▶ 结果校验（空值/报错重试）
  ▲                        │                                        │
  │                        └── 校验失败：把原因回喂模型让它重发 ──────┤
  └────────────── 观测结果写回上下文 ◀──────────────────────────────┘
                                       │
                               无工具调用 → 最终答案
```

| 文件 | 职责 |
| --- | --- |
| `agent/loop.py` | 手写 agent loop，核心 ~120 行，含四道防护 |
| `agent/tools.py` | 工具注册表：JSON Schema + 执行器 + 沙箱护栏 |
| `agent/llm.py` | 统一 LLM 客户端，支持任意 OpenAI 兼容接口与离线 mock |
| `evals/gen_tasks.py` | 生成评测集，标准答案直接来自真实 SQL 查询，不与代码漂移 |
| `evals/run_eval.py` | A/B 跑分 + 失败归因 + 生成报告 |

四道防护：

1. **参数校验**：缺字段、类型错、多余参数，全部转成错误信息回喂模型，而不是抛异常崩掉整个 loop；
2. **结果校验**：工具返回空值（`[]` / `{}` / `null`）时提示重试，避免把空观测当成事实写进上下文；
3. **步数护栏**：超过 `max_steps` 强制结束并记录失败原因，防止死循环烧 token；
4. **沙箱与只读**：文件读写限制在 `evals/_work`，数据库只允许 `SELECT`。

## 评测

评测集共 **51 条任务**（简单 20 / 中等 20 / 困难 11），按覆盖的工具链路和能力要求分层：

| 难度 | 例子 | 考察点 |
| --- | --- | --- |
| easy | 「今天是几号」「计算 365 × 24」 | 是否会调用工具而不是靠模型记忆/心算 |
| medium | 「算出 A 部门与 B 部门的平均工资差」「查询后写入文件」 | 两步以上、跨工具协作 |
| hard | 「统计各部门平均工资，找出最高的并写入文件」 | 三步以上链式调用与结果落盘 |

判定方式：数值类比对「宽容差数值」，文件类比对「目标文件是否包含结果」，日期类比对「是否调用了日期工具而非编造」。

跑分结果见 **[evals/report.md](evals/report.md)**，一次 A/B 的输出如下：

| 版本 | 任务成功率 | 平均步数 | 工具调用错误率 |
| --- | --- | --- | --- |
| baseline（无校验） | 92.2%（47/51） | 3.0 | 5.9% |
| hardened（参数+结果校验） | 92.2%（47/51） | 3.1 | 7.3% |

> 上表是接入 **DeepSeek（deepseek-chat）** 后跑出的真实成绩。一个值得讲的现象：**强模型本身已经把成功率拉到 92.2%，两版几乎持平**——这说明「校验」的价值在真实模型上从「救命」变成了「兜底」：它不会明显拉升成功率，但能把参数 / 结果类错误在落地前拦下来重发，避免把垃圾写进上下文。对比 mock 模式下两版都是 27.5%（正则规划器参数永远合法），更能看清防护的真实定位。

### 失败归因

`evals/run_eval.py` 会把每一条失败任务自动归到以下类别，直接写进报告：

| 失败类型 | 典型原因 | 修复动作 |
| --- | --- | --- |
| 工具参数错误 | 模型传了自然语言给 calculator、漏了必填字段 | 参数校验 + 错误信息回喂重发 |
| 工具执行报错 | SQL 字段名写错、文件不存在 | 错误详情回传，允许改策略重试 |
| 未调用日期工具（幻觉） | 直接凭训练记忆回答「今天是几号」 | system prompt 明确禁止，评测集专门覆盖 |
| 文件未写出 | 调用了 file_write 但路径写在子目录 | 沙箱函数强制 basename 归一化 |
| 超过最大步数 | 反复重试同一失败动作 | 步数上限 + trace 记录 |

## 踩坑记录

1. **工具异常不能往外抛**：一开始 `file_read` 读不存在的文件直接报 `FileNotFoundError`，整个 loop 崩掉；改成统一返回 `{"ok": False, "result": ...}`，让错误成为上下文的一部分。
2. ** assistant 消息必须原样回填**：带 `tool_calls` 的那条 assistant 消息要先 append 回上下文，否则部分服务端会报「tool_call_id 无对应消息」。
3. **每条任务要用独立沙箱**：文件类任务会互相污染（上一题写的 `report.md` 让下一题「未写文件」被误判为成功），评测时必须逐题清空工作目录。
4. **评测答案不能手写常量**：日期、数据库聚合值这类答案必须从真实数据源现算（`gen_tasks.py` 里直接查 SQLite），否则代码一改标准答案就失效。
